## 三、解题思路与设计实现

本次没有重新设计产品，而是把第三次作业中的原型逐项变成代码。F1-F7 与页面文件一一对应，三条原流程保持不变。数据层抽象为 `ItemRepository`，默认使用本地存储，同时提供阿里云 `uniCloud` 适配器，因此第一版不依赖服务器也能完整验收，后续更换数据源不需要重写页面。

关键实现点：

- 发布前在领域层和页面上同时校验必填项与长度。
- 联系方式默认隐藏，点击后显示并一键复制。
- 状态文案严格区分寻物和招领。
- 状态、编辑、删除写回 Repository 后，全局 Store 立即刷新所有页面。
- 可选照片通过 `uni.chooseImage` 选择，并保存到应用数据目录。

## 四、关键代码

### 1. Repository 统一接口

页面只调用 `listItems/getItem/create/update/remove/changeStatus`，本地与云实现共享相同接口。

### 2. 状态文案

```js
if (item.type === "lost") {
  return item.status === "resolved" ? "已找回" : "寻找中";
}
return item.status === "resolved" ? "已归还" : "待认领";
```

### 3. 本地数据持久化

页面统一通过 Repository 读写数据，本地实现会把最新快照保存到 `uni storage`，应用重启后仍能恢复。

## 九、异常与结对困难

主要困难是 HBuilderX 5.24 首次使用需要下载约 91 MB 的 `uniapp-cli-vite`，而 DCloud Android SDK 版本为 5.26。解决思路是先保证本地编译工具完整，再生成 `appResource`，最后交给 `android-local` 的 Gradle 工程打包，不依赖云打包。离线 SDK 还要求 AppID、包名和证书 SHA1 对应的 `dcloud_appkey`，该值必须从 DCloud 开发者中心申请，不能硬编码到仓库。
